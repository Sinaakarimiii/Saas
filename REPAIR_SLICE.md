# Repair server slice: intake, decision, repair completion, replacement custody, and the return path

This isolated copy of `org_platform` contains an evolving database and application slice for repair cases. It does not modify the source checkout. The migrations are in `supabase/migrations/`, through `20260928170335_replacement_original_scrap.sql`.

Implemented:

- Create a repair case with a durable tracking code, actor, version, and event.
- Record physical receipt, location, custodian, items, and the matched IMEI with a private photo of the device label.
- Require an existing JPG, PNG, or WebP object of at most 5 MB, uploaded by the receiver under this organization and case, before verifying an IMEI. The bucket is private and the application displays a short-lived signed link to the attached photo.
- Enforce one open case per verified IMEI across an organization. A second case needs `repair.case.duplicate.override`, a reason, and a unique approval reference. A case creator may also hold this permission.
- Reject silent correction when a 15-digit intake identifier differs from the physically verified IMEI.
- Check active organization membership and specific permissions in the database; allow client reads through RLS, but mutations only through checked functions.
- Serialize same-device receipts and make command retries idempotent; reject stale case versions.
- Show a repair list, intake form, case detail with the seven main stage labels, and physical receipt form in the organization app. The forms call the checked database commands through authenticated Server Actions.
- Permit T01 (intake to diagnosis) only after physical receipt, recorded location/custodian, model/issue, and a traceable raw or verified device identifier. Permit T10 (diagnosis back to intake) with its own permission. Stage transitions use a two-button confirmation dialog without a mandatory note, expected case version, idempotency, and an actor/time/from/to event.
- Save append-only diagnosis revisions with findings, technical condition, recommended action, and warranty coverage (including explicit pending). A separate `repair.diagnosis.finalize` permission finalizes the latest draft. T02 (diagnosis to decision) requires both its transition permission and a final diagnosis from the current diagnosis visit; returning to intake and re-entering diagnosis cannot reuse an old final revision. All three commands audit actor and revision and reject stale case versions.
- Save immutable action-plan revisions in decision stage for repair, replacement, or return. Financial basis, amount in IRR, replacement reason/model, proposed original-device disposition, and parts strategy are distinct fields. The route must match the final diagnosis. Current proposal entry supports warranty, customer-paid, or cost-free return; discounted and organizational-support bases await separate approval policies.
- Record customer responses with channel, person/role, source reference, stated time, and authority reference for a representative. Record replacement approval through independent `repair.replacement.approve`; a plan creator with that permission may approve their own proposal. Both kinds are bound to one plan revision; a new proposal does not inherit old approvals. Rejection is retained as history. These records do not execute a physical repair/replacement or move inventory.
- Permit T03 (decision to repair) for the current finalized diagnosis and matching plan only when financial coverage is resolved, current-plan customer approval exists for a paid repair, and either the plan needs no parts or every listed part requirement of the current plan has an active full-quantity reservation. A parts-dependent plan with no requirement lines remains blocked. Permit T04 (decision to replacement) only with matching coverage, customer approval even at zero cost, and an independent approved replacement decision for the current plan. The server checks these under a case lock with version and idempotency controls. Stage transition enters an execution queue; it does not record work, consume stock, or change physical custody.
- Permit T05 (decision to outgoing control) only for a current zero-cost return plan linked to the latest final diagnosis and a separately authorized manual notification tied to that plan revision. The notification records channel, person, time, and reference; authorization selects the versioned `return_outgoing_v1` protocol. Neither this command nor T05 claims that QC or physical handover has happened. Revising the plan invalidates the prior authorization for transition.
- Record append-only, versioned return outgoing checks for the verified device, current return plan and authorization. Identity, received items, disclosed technical condition and transport safety each require a result and evidence reference. A failed result remains visible but cannot be released. An independent `repair.quality.release` permission releases only the latest passing check; a later check invalidates the prior release for T08. The intended recipient and authority reference are recorded for handover preparation, including a colleague option. T08 moves only this guarded return path from test to delivery and does not claim physical handover or device health.
- Assign every new case initially to its creator, independently of physical custody. A `case.assign` holder can request transfer to an active organization member with a unique reference; one request may be pending per case. Only the addressed member with the matching accept/reject permission can answer, and only the requester with withdraw permission can withdraw. Rejection and withdrawal require a reason and unique resolution reference. The assignee changes only on acceptance, which closes the prior responsibility period and starts a new one. The repair list shows requests addressed to the signed-in user; the case detail shows the current assignee and request history. All commands use organization membership, permission, actor, version, idempotency and case-row checks. Assignment never changes physical location or custodian.
- Record documented stock receipts into an organization-wide part catalog, define multiple part requirements for the current action-plan revision, and reserve full quantities from free stock under a part-row lock. A new plan revision releases old active reservations. Receipt references are unique per organization; reservation is not consumption. These commands have distinct permissions, expected case versions for plan operations, idempotency, audit events, RLS reads, and database-only writes. The decision page displays available stock and readiness. Serialized part tracking, staged repair plans, and physical evidence verification remain future slices.
- In repair stage, record part consumption against an active reservation and an action description with a unique issue reference. Each transaction reduces usable stock and reserved remainder together. A documented command releases unused reserved remainder without changing physical stock. A consumed part may be returned only up to its unreturned consumption quantity; the return is linked to the original issue and held in quarantine, never added to usable stock automatically. All three commands use separate permissions, case versions, idempotency, case→stock locks, append-only movement or release records, and audit events. The repair page shows these actions and their history. Serial-number tracking is not yet implemented.
- Resolve each quarantined return through a documented inspection decision, in full or in parts. `repair.part.quarantine.restock` permits returning inspected usable quantity to free stock; `repair.part.quarantine.reject` records rejected quantity in separate holding without increasing free stock. Resolution quantity cannot exceed the returned quantity; decisions retain actor, case, source return, note, evidence reference and unique decision reference. Idempotency and case→stock→return locks protect retries and concurrent decisions. Rejection is not scrapping or physical disposal.
- Track the original verified device’s confirmed physical position separately from case assignment. A documented baseline binds the recorded location to an active member. The confirmed custodian alone may release it with a carrier, unique issue reference, and evidence; one in-transit transfer per device is allowed across the organization. The addressed member with `custody.transfer.accept` records actual destination receipt and only then updates the confirmed location and custodian. The source custodian with `custody.transfer.return` can record physical return without changing the confirmed position. Each command checks its own permission, active membership, device/case identity, case version and idempotency, and retains an audit event and independent transfer history. Replacement-device transfers use a separate command path described below.
- Register serial-numbered replacement stock with a unique organization IMEI, physical location, active custodian, and evidence/reference under `replacement.stock.receive`. In the replacement stage, `replacement.stock.allocate` locks the case and stock row, checks the current approved plan and exact model, and reserves one unit exclusively for the case. Allocation records an immutable history event and creates a separate confirmed custody baseline for the replacement unit without changing the original device position. Repeated commands are idempotent; a stock unit cannot be received twice, allocated twice, or admitted as an original repair device. Allocation does not execute the replacement, settle finances, or deliver the device.
- Execute the physical replacement with `repair.replacement.execute` and T07 permission, a unique execution reference, and separate evidence. The command binds the current approved plan, original verified device, allocated replacement IMEI and allocation, checks both staff custody positions and unresolved transfers/discrepancies, then atomically records the execution and moves the case to test. A database guard rejects direct replacement-to-test updates without that execution record. The original device's proposed disposition remains pending; allocation stays attached to the case. Test, quality release, payment settlement and delivery of a replacement remain separate work.
- Move an allocated replacement device between active organization members through separate release and receipt commands using the same custody permissions and append-only transfer ledger. The original and replacement devices can have independent open transfers. Release leaves confirmed positions unchanged; actual destination acceptance updates both the replacement custody position and its stock location/custodian atomically, while original case location fields stay intact. A return to source closes only that device's transfer. The replacement case panel shows its own transfer history and receipt actions.
- Apply the same versioned discrepancy ledger to the allocated replacement device: the intended recipient can record identity, destination, or damage issues; an open issue blocks destination acceptance. Identity/destination resolution permits a fresh destination receipt while the transfer remains open, or a new transfer after a documented return. Damage requires a physical return to the source before resolution and increments the case quality epoch. The replacement panel shows the blocker, responsible member, due time, evidence, resolution and history independently of the original device.
- Complete physical repair with a separate `repair.complete` permission and T06 transition permission. The command binds the current repair plan, verified original device and chosen `repair_functional_v1` test protocol; it requires a documented work description/reference for a no-parts repair, or full recorded consumption and no active reservation for a parts-dependent plan. An open device transfer or discrepancy blocks completion. A versioned, immutable completion record and stage event are written atomically before entering test. This selects the test protocol; it does not claim that a functional test has run or passed.
- Record versioned functional tests after repair completion, with separate results and evidence for identity/items, power, positioning/communication and configuration/services. The first two are mandatory; the last two may be marked not applicable only with a recorded reason. The database derives the overall result from the items, retains failed attempts, and permits independent quality release only for the latest passing test bound to the current plan, completion, device, test visit and damage epoch. An open transfer or discrepancy blocks recording/release. This does not yet authorize T08 or delivery of a paid repair; financial and delivery guards remain to be implemented.
- Record the same versioned functional controls after physical replacement execution, bound to its execution record and the actual replacement-device serial. The repaired-device and replacement-device tests have distinct protocol and source constraints; the latest passing replacement test needs independent quality release. Failed attempts, stale versions, missing permissions and unresolved custody block release.
- Record replacement outgoing QC with its own `repair.replacement.outgoing_qc.record` permission and `replacement_outgoing_v1` protocol. The four controls and intended owner/representative/colleague bind to the latest released functional test of the executed replacement serial. Independent quality release applies to the latest passing control only. A dedicated T08 command rechecks execution, allocated stock, both device custody positions, open custody/assignment blockers, current test/QC releases and net settlement after verified receipts, approved credit and refunds. A database trigger protects direct stage writes. T08 leaves stock allocated and does not record physical handover, settle the original-device disposition or close the case; these remain the next slice.
- Record payment evidence for the current customer-paid plan revision with a positive IRR amount, method, unique organization transaction reference, and evidence reference. A separate `repair.payment.verify` permission and unique reconciliation reference verifies each receipt; only verified amounts count toward the displayed balance, and verification cannot exceed the plan amount. Case versioning, idempotency, case-row serialization, RLS reads and database-only writes apply. A revised plan cannot inherit or verify old-plan receipts. This is documented manual reconciliation, not a payment-gateway transaction or a delivery release; refunds and cross-plan credit require the separate approval flows described below.
- Correct a mistaken current-plan payment document before delivery with independent `repair.payment.correct` permission, reason, explanation, unique correction reference, and evidence. The original receipt and verification remain in history; an append-only correction removes that receipt from the active verified balance. A corrected receipt cannot be verified later or corrected twice. The repaired-device handover guard rechecks this balance, so correcting a fully paid case blocks T08 until new valid evidence is verified. Corrections are permitted in decision, repair, replacement, or test, and not after delivery. This records an evidence correction only: it does not send money back, transfer funds to a revised plan, or create customer credit.
- Record a separate outgoing control for a repaired device only after its latest passing functional test has an independent quality release. Identity, included items, post-repair condition and transport safety each have a result and evidence; the intended recipient may be owner, authorized representative or colleague, with authority reference for the latter two. Failed checks remain in history. Only the latest passing check bound to the current test, plan, device, test visit and damage epoch can receive an independent quality release. Open custody transfer or discrepancy blocks both commands. This control records readiness, not handover.
- Transfer part or all of a verified, uncorrected receipt from an older plan revision to the current customer-paid repair/replacement plan with `repair.payment.credit.request`, a unique request reference and evidence. A different person with `repair.payment.credit.approve` records an independent approval reference; only then does the credit count toward current-plan settlement. Approval rechecks remaining source value and target-plan capacity under the case lock, and retries are idempotent. The original receipt stays bound to its plan, approved allocations remain in history, and pending requests never count as paid. Existing receipt verification and repaired-device handover now include approved credit when checking the plan cap/settlement. A transferred source receipt cannot be corrected through the normal command, and a database guard rejects inserting a correction after a transfer. The case page shows the source, amount and approval state. Actual refunds use the separate flow below.
- Request an actual refund from any verified, uncorrected payment receipt with `repair.payment.refund.request`, amount, reason and unique request reference. This request is not yet money movement. A different person with `repair.payment.refund.approve` confirms the outbound method, unique transaction reference, receipt evidence reference and separate approval reference. Only then does the refunded amount reduce the balance of its source plan, if current, and the source available for future credit transfers. Approval rechecks that source under the case lock; correction of a refunded receipt is blocked. Refunds can be recorded after the case closes without rewriting the historical delivery event. The page shows pending and approved refunds across all plan revisions. This is manual reconciliation against an external receipt reference, not a payment-gateway payout or uploaded proof validation. Refunding credit already allocated to another plan requires a separate reversal policy and is not implemented.
- Permit T08 for a repaired device through a separate checked command only when the latest functional test and outgoing check have independent releases, the staff custody baseline exists, custody/assignment blockers are clear, and the current plan is either zero-cost warranty or fully covered by net verified payment evidence after approved refunds and approved transferred credit. Partial or unverified payments do not release a customer-paid case. This T08 records stage movement, not physical delivery. Internal staff transfers must be completed before repaired T08. An in-person receipt must match the released check's exact recipient and authority, be entered by the confirmed device custodian, and include a unique reference and independent evidence. Receipt atomically changes physical custody to the recipient. T09 closes the repaired case only after rechecking readiness and that receipt; direct stage updates cannot bypass the guards.
- For a repaired device, the confirmed custodian can also register a postal/courier dispatch against its released repair outgoing check. Dispatch transfers custody to the carrier but does not count as customer receipt. A separately permitted destination receipt must match the exact dispatch, device, check, recipient and authority, and use a different reference and evidence. An open shipment incident blocks receipt. Confirmed destination receipt transfers custody to the recipient; only then may T09 close the case. Direct handover and shipment are mutually exclusive. A damaged repaired shipment follows the same documented physical-return and incident workflow as an unrepaired return; T11 moves it back to test only after return and a changed damage epoch, then requires fresh functional test and outgoing QC, release, T08 and a new shipment. The earlier dispatch remains in history.
- Record internal acceptance discrepancies for the original device as identity mismatch, destination mismatch, or damage, with independent record/resolve permissions, a unique reference, evidence, responsible member, deadline, transfer version, and event history. An open discrepancy blocks destination acceptance and a subsequent release. Resolving identity/destination discrepancies only permits a fresh destination receipt. Damage requires a separate physical return receipt before documented resolution. Each damage report increments the case damage epoch; outgoing QC binds that epoch, and an open damage discrepancy blocks a new check. Prior checks and quality releases cannot be reused after damage, even after resolution. The database blocks stale quality release and T08, and the return-control panel explains the required fresh check and independent quality release. For a return case damaged after T08, permission T11 allows delivery-to-test recovery only after a physical return receipt. The case then needs documented discrepancy resolution, a new outgoing check, independent quality release, and another T08. The repairs list shows open destination receipts and discrepancies assigned to the signed-in user independently of case pagination.
- For a zero-cost return in delivery, the confirmed device custodian with `repair.delivery.receive` can record an in-person receipt tied to the latest released QC, exact recipient/authority, and independent unique receipt reference/evidence. The database rejects an open assignment, device transfer or discrepancy. Alternatively, the confirmed custodian with `repair.delivery.dispatch` records a postal/courier dispatch with carrier, destination address/recipient, tracking code, unique dispatch reference, and evidence. This is an in-transit carrier custody record, not a receipt. A holder of `repair.delivery.confirm_receipt` records the actual destination receipt against that exact dispatch and QC with a different reference and evidence. Direct handover and shipment receipts are mutually exclusive. A separate `case.close` holder can perform T09 only after a valid receipt and a fresh recheck of blockers/QC; closure saves an outcome, receipt ID, timestamp and event. These commands are versioned and idempotent. A stage-update guard blocks direct closure without a valid receipt. Confirmed custody now changes atomically from staff to carrier on dispatch and to the actual recipient on either type of receipt. A damaged attempt returned physically restores staff custody. A later case for the same device can establish a new staff baseline only after the previous case is closed, its recipient receipt matches the last external position, and the new case has a physical intake plus fresh documented inspection. Internal movement cannot use an external holder as its source. Recipient identity verification beyond the recorded evidence remains future work.
- A postal/courier dispatch can have a versioned loss, damage, or delivery-discrepancy incident tied to that exact shipment, with a unique reference, evidence, responsible member, and due time. An open incident blocks destination receipt and T09 at the database boundary. Follow-up is append-only, has a unique reference and outcome, and changes only the responsible member and next due time; it cannot clear the blocker. Separate permission and documented resolution can resume a lost/disputed shipment, but the recipient receipt remains independent. Damage requires an independent physical-return receipt by an authorized staff member, with location, condition and evidence. The old dispatch becomes returned, the incident is resolved by that receipt, and the damage epoch invalidates the old QC. T11 requires this return; fresh QC and release, T08, a new dispatch, independent destination receipt, and T09 complete the corrective path. The prior dispatch stays in case history. Case detail shows these actions. The repair list now previews all visible open shipment incidents across the organization; a paginated queue shows all or only those assigned to the current user, ordered by due time with overdue priority and explicit Tehran time, and links to the case follow-up panel.
- Show the seven primary milestones with repair/replacement as one alternative action milestone; separate forward progress from return in the case UI.

New permissions are automatically granted to organization owners, consistent with existing organization bootstrap. Other roles need explicit grants. Existing local cases created before the evidence migration retain their legacy text references; the detail page marks these as unavailable files. The upload proves a file exists and is associated with the receiving user and case; human review of photo quality and actual label contents remains a separate workflow step. T01 currently uses the physical custodian as a receipt fact; stage transitions do not automatically request or accept work assignment.

The functional SQL tests roll back their fixtures. The two-session race test removes its fixture after checking that only one same-IMEI receipt commits. The Storage/API test creates a disposable account and organization, rejects a missing photo, uploads real image bytes, verifies receipt and private download, saves and reads diagnosis, then records a decision plan and customer approval through the Data API before removing its fixture. None of these tests targets the source project's local database.

Application checks: `next typegen`, `npm run typecheck`, targeted ESLint, and `next build --webpack` pass. Turbopack cannot build this isolated copy because its `node_modules` symlink points outside the copied project root; Webpack builds successfully. In the isolated running app, case creation, physical receipt, duplicate rejection, permitted exception, and desktop/mobile layouts were checked through the browser.

Policy decided by the user: verified payment from an older plan may reach a new plan only through a separately recorded and independently approved credit transfer; an actual refund requires evidence of money leaving and approval by a second person. Both flows are implemented with independent approval. Old-plan payments never silently count toward current-plan settlement and evidence correction is not a refund.

Replacement in-person delivery now records the approved recipient and independent receipt reference/evidence, checks the current custodian, revalidates QC, settlement and custody blockers, and atomically issues the allocated replacement stock. The physical receipt moves only the replacement custody to the recipient; the case retains the original verified device and its custody metadata. Issued stock preserves allocation provenance and cannot be reallocated. For a plan requiring original return to the customer, a separate permission and current original-device custodian can now record an independent original-device receipt and condition/items note. It uses the approved replacement recipient/authority, preserves the original serial, and moves original custody to that recipient. T09 rechecks both receipts, issued stock, current plan/execution, settlement, releases and open blockers, then closes with outcome `replaced_original_returned`. A later physical intake can establish a new original-device custody baseline using this return receipt after the previous case closes. User-approved warehouse policy: a documented handover to the responsible warehouse person completes the original-device disposition for this repair case; refurbishing or parts processing does not need to finish first. For `refurbish_proposed` / `parts_proposed`, the original-device internal custody transfer must be accepted after replacement execution. Its destination custodian, with `repair.replacement.warehouse_receive`, records the condition/items and finalizes `refurbish_received` / `parts_received`. The receipt copies reference, evidence, location and recipient from that accepted transfer rather than accepting a second typed receipt. It binds the original serial, current execution and transfer. T09 rechecks finance, replacement receipt/QC, open blockers and the unchanged warehouse custody, then closes with the specific warehouse-received outcome. Moving the original after finalization invalidates that closure check. After accepting a new transfer, the destination custodian can record a new warehouse receipt; the complete previous and current receipts are retained in the audit event. Same-transfer overwrites are rejected. This is receipt into a warehouse process, not proof of refurbishing, parts recovery or saleable inventory. The user-approved scrap policy is implemented through `repair.replacement.scrap.record` and `repair.replacement.scrap.approve`. After replacement delivery, the current original-device custodian records actual execution reference, evidence reference and note, bound to the current execution and original serial. Recording changes original custody to terminal `scrapped` immediately, retaining the execution location and actor/time; it is never reported as staff-held while awaiting approval. Database guards prevent subsequent custody mutation/deletion and receipt into a new repair case. A different active organization member with the independent approval permission reviews and confirms the record; the recorder cannot self-approve even with both permissions. Both commands lock the case, recheck settlement, QC, delivery and open blockers, enforce expected version and replay identity, and audit the complete record. T09 additionally requires the second-person approval and matching terminal custody, then closes with `replaced_original_scrapped`. The UI displays the original IMEI, evidence, recorder, approval state and two-button confirmation dialogs. There is no automatic scrap or stock restock. Evidence is a recorded reference; uploaded execution-document verification and correction/reversal of a factual scrap declaration are not implemented. The scrap UI path was verified in the production build through two real local Auth accounts used sequentially: cancel, record, blocked self-approval/closure, independent confirmation, then permitted closure. The evidence/approval history remains visible after closure. See `docs/REPAIR_BROWSER_VALIDATION.md`; simultaneous-session race and other replacement UI paths remain pending. Receipt evidence is a recorded reference; uploaded signature verification is not implemented. Replacement post/courier delivery is implemented with current-custodian dispatch and a separately authorized destination confirmation. Both commands bind the executed replacement serial, current released outgoing check, approved recipient/authority, settlement and custody blockers. Dispatch moves only replacement custody to the carrier and preserves original-case location/custodian metadata; stock stays allocated until the destination receipt atomically issues it. An open shipment incident blocks destination receipt and closure. Incidents bind the dispatched serial. Damage requires documented physical return; it restores replacement stock/location/custodian, increments the quality epoch and preserves original-device metadata. T11 returns to testing; fresh functional test, quality release, outgoing check and release are required before T08 and a new shipment. The old attempt and return remain in shipment history. Original-device disposition remains independently required for closure after remote receipt. The post/courier/damage-loop SQL scenarios and repaired-route regressions pass; browser validation of the new replacement shipment UI remains pending.

Issued replacement re-entry is supported after the previous replacement case closes. A fresh physical intake must provide its own case-scoped IMEI photo and resolve to the same device ID. The stock guard checks the immutable issue receipt, issuance time, execution/plan and closed previous case; available or allocated stock and replacements from still-open cases remain inadmissible. The new intake establishes a fresh staff custody baseline using the old delivery receipt, without changing the prior case, receipt or stock issue. The ordinary organization-wide duplicate rule still applies. The original-return scenario test covers these eligibility boundaries, replay, new custody, T01, provenance preservation and duplicate rejection. This slice has database regression/security verification; browser validation of replacement re-entry remains pending.
