# ۰۲ — مفاهیم پایه‌ی Process (Concept Glossary)

> این سند مبنای واژگانی کل Research است. هر سند دیگر در این پوشه این تعاریف را به‌عنوان مرجع فرض می‌کند. زبان مرجع (Canonical) برای شناسه‌ها انگلیسی است؛ توضیح فارسی برای فهم کاربردی آمده.

هر واژه سه بخش دارد: **تعریف**، **چرا این تعریف** (مبتنی بر کدام منبع/استدلال)، و **اشتباه رایج** (چیزی که معمولاً با آن قاطی می‌شود).

---

## ۱. سلسله‌مراتب سازمانی (چهارچوب، نه داده)

| اصطلاح | تعریف |
|---|---|
| **Organization** | یک Tenant مستقل در SaaS — واحدی که داده‌اش کاملاً از سایر Tenantها ایزوله است. معادل `organizations` در پروژه‌ی فعلی. |
| **Industry** | صنعتی که یک Organization در آن فعالیت می‌کند (مثلاً Healthcare، Retail). یک برچسب طبقه‌بندی روی Organization است، نه یک سطح در سلسله‌مراتب فرایند. |
| **Business Domain** | حوزه‌ی کاری Cross-Functional که در همه‌ی صنایع تکرار می‌شود (HR، Finance، Procurement، IT، …). معادل تقریبی APQC **Category** (سطح ۱). |
| **Department** | واحد سازمانی واقعی داخل یک Organization خاص (مثلاً «واحد منابع انسانی شرکت X»). برخلاف Domain، Department به یک Organization خاص متعلق است، نه یک مفهوم عمومی. |
| **Function** | زیرمجموعه‌ی یک Domain — گروهی از فرایندهای هم‌راستا (مثلاً درون Domain «Finance»، Functionهای «Accounts Payable»، «Accounts Receivable»). معادل تقریبی APQC **Process Group** (سطح ۲). |
| **Business Capability** | توانایی‌ای که سازمان دارد صرف‌نظر از اینکه چگونه اجرا می‌شود (مثلاً «توانایی مدیریت درخواست مرخصی»). Capability با Process فرق دارد: Capability یعنی «می‌تواند»، Process یعنی «چگونه واقعاً انجام می‌دهد». یک Capability می‌تواند صفر، یک یا چند Process پیاده‌سازی‌شده داشته باشد. |
| **Value Stream** | زنجیره‌ی End-to-End از فعالیت‌هایی که مستقیماً برای یک ذی‌نفع (معمولاً مشتری) ارزش تولید می‌کنند؛ معمولاً چند Domain را قطع می‌کند (مثلاً «از سفارش تا تحویل» چند واحد را درگیر می‌کند). Value Stream عمودی به مشتری نگاه می‌کند؛ Domain افقی به تخصص سازمانی. |

## ۲. سلسله‌مراتب طبقه‌بندی فرایند (Taxonomy، بر پایه‌ی APQC PCF — نگاه کنید به [۰۳](03-industry-taxonomy.md))

| اصطلاح | تعریف | معادل APQC PCF (تأییدشده از منبع اصلی) |
|---|---|---|
| **Process Category** | بالاترین سطح طبقه‌بندی (مثلاً «Manage Financial Resources»). | Level 1 — Category (کد یک‌رقمی، مثل `9.0`) |
| **Process Group** | گروهی از فرایندهای هم‌جهت داخل یک Category. | Level 2 — Process Group (کد دو-رقمی، مثل `9.1`) |
| **Business Process** | یک فرایند مشخص با شروع/پایان قابل‌تشخیص که یک نتیجه‌ی کسب‌وکاری تولید می‌کند (مثلاً «Process Accounts Payable»). | Level 3 — Process (مثل `9.1.1`) |
| **Sub Process** | تجزیه‌ی اختیاری یک Process به Processهای کوچک‌تر با همان ماهیت (خود APQC هم گاهی این کار را می‌کند، مثلاً `7.3.4` زیر `7.3`). | تعریف رسمی APQC ندارد؛ یک لایه‌ی اختیاری میانی است که خود محصول اضافه می‌کند. |
| **Activity** | یک گام کلیدی برای اجرای یک Process. | Level 4 — Activity (مثل `9.1.1.1`) |
| **Task** | ریزترین واحد کار برای اجرای یک Activity؛ طبق تعریف صریح APQC «به‌طور یکدست Level-بندی نشده» و بین سازمان‌ها/صنایع متفاوت است. | Level 5 — Task |

**نکته‌ی کلیدی از Research (تأییدشده از متن اصلی APQC):** PCF صراحتاً ترتیب اجرا را کدگذاری نمی‌کند («numbered ascendingly... does not imply order»). یعنی Taxonomy فقط **طبقه‌بندی** است، نه **نقشه‌ی اجرا**. مرز دقیق بین Taxonomy (این سند + ۰۳/۰۴/۰۵) و Execution (سند [۰۷](07-workflow-node-catalog.md) و [۰۸](08-process-engine-architecture.md)) همین‌جاست: از Task به پایین، مسئولیت محصول شروع می‌شود، نه APQC.

## ۳. واحدهای اجرا (Runtime — چیزی که واقعاً اتفاق می‌افتد)

| اصطلاح | تعریف | چرا از مفهوم بالا جداست |
|---|---|---|
| **Workflow** | نمایش **اجرایی/قابل‌ماشین‌خواندن** یک Business Process — گراف واقعی از Nodeها/Edgeها که موتور اجرا می‌کند. | Process «چه کاری باید انجام شود و چرا» را طبقه‌بندی می‌کند؛ Workflow «دقیقاً با چه ترتیب/شرط/Actor» آن را اجرا می‌کند. یک Process می‌تواند چند پیاده‌سازی Workflow متفاوت در سازمان‌های مختلف داشته باشد (نگاه کنید به تفاوت Process/Workflow در بخش ۴). |
| **Case** | یک نمونه‌ی در حال پیگیری از یک فرایند **غیرخطی/باز-تا-بسته** که معمولاً چند Work Item مستقل درون خودش دارد و پایانش از قبل مشخص نیست (مثلاً یک پرونده‌ی بازرسی که ممکن است چند بار باز/بسته شود). | برخلاف Workflow Instance که مسیر از پیش تعریف‌شده دارد، Case بیشتر شبیه یک «پوشه» است که فعالیت‌های نامنظم به آن اضافه می‌شوند (الگوی Pega Case Management). |
| **Project** | مجموعه‌ای از Taskها/Milestoneهای **یک‌بارمصرف** با هدف، بودجه و تاریخ پایان مشخص که برای رسیدن به یک خروجی منحصربه‌فرد اجرا می‌شود. | Process تکرارپذیر است (صدها بار اجرا می‌شود با همان الگو)؛ Project یک‌بار برای یک هدف خاص اجرا می‌شود، حتی اگر از یک Template پروژه استفاده کند. |
| **Workflow Instance** | یک اجرای مشخص و زمان‌دار از یک Workflow Definition (نسخه‌ی مشخص) — معادل یک ردیف در `workflow_instances`. | نگاه کنید به [۱۵-versioning](15-versioning.md) برای تفاوت دقیق با Workflow Version. |
| **Work Item** | واحد کار قابل‌تخصیص به یک Actor درون یک Instance — می‌تواند Task، Approval، Form یا Event باشد. | Work Item چتر بالاتر از Task/Approval/Form است؛ هر Node اجرایی که به یک Actor نیاز دارد یک Work Item تولید می‌کند. |
| **Request** | ورودی اولیه‌ای که یک Instance را آغاز می‌کند — بیان نیاز توسط یک Actor (مثلاً «درخواست مرخصی»). | نگاه کنید به تفاوت Form/Request در بخش ۴. |
| **Ticket** | یک نوع خاص از Case که معمولاً برای رهگیری یک مسئله/درخواست خدمات با چرخه‌ی عمر مشخص (باز→در حال بررسی→بسته) استفاده می‌شود؛ در این پروژه معادل جدول `tickets` موجود است. | نگاه کنید به تفاوت Case/Ticket در بخش ۴. |

## ۴. تفاوت‌های صریح خواسته‌شده

### Process در برابر Workflow
**Process** طبقه‌بندی مفهومیِ «چه کاری» است (لایه‌ی Taxonomy، از APQC). **Workflow** پیاده‌سازیِ اجرایی «چگونه» است (گراف Nodeها). یک Process («تأیید مرخصی») می‌تواند در سازمان A یک Workflow تک‌مرحله‌ای و در سازمان B یک Workflow سه‌سطحی موازی باشد — هر دو همان Process را پیاده‌سازی می‌کنند اما Workflow متفاوتی دارند. **پیامد طراحی:** `processes` (Catalog/Taxonomy، بدون گراف) باید از `workflow_templates` (گراف قابل‌اجرا) جدا باشد؛ یک `process` می‌تواند صفر یا چند `workflow_template` پیوندشده داشته باشد (نگاه کنید به [۰۹](09-data-model.md)).

### Process در برابر Project
Process **تکرارپذیر** و **الگووار** است (همان مسیر بارها اجرا می‌شود: صدها «تیکت خرید»). Project **یک‌بارمصرف** و **هدف‌محور** است، حتی وقتی از یک Template ساخته می‌شود (دو پروژه‌ی «راه‌اندازی شعبه‌ی جدید» شبیه‌اند اما هرکدام Milestoneهای منحصربه‌فرد خودشان را دارند و با پایان پروژه، آن نمونه تمام می‌شود، نه تکرار). عملاً: Workflow Instance مربوط به یک Process معمولاً چند دقیقه تا چند هفته طول می‌کشد؛ Project معمولاً هفته‌ها تا ماه‌ها. **پیامد طراحی:** ماژول Task Manager/Project طبق ROADMAP.md موتور گردش‌کار جدا نمی‌سازد؛ بلکه از همین Workflow Engine برای «فرایندهای مدیریت پروژه» (مثل Change Request داخل پروژه) استفاده می‌کند، اما Projectها و Milestoneهای خودشان Entity جدا هستند، نه Instance گردش‌کار.

### Task در برابر Activity
**Activity** سطح طبقه‌بندی (Level 4 در APQC) — «یک گام کلیدی» در سطح مفهومی، معمولاً چند Task را دربرمی‌گیرد و مستقیماً قابل‌اجرا نیست. **Task** یا (الف) ریزترین سطح Taxonomy (Level 5 APQC) یا (ب) در زمینه‌ی Runtime، یک Work Item مشخص که به یک نفر تخصیص داده شده. برای جلوگیری از ابهام، در این سند **Task همیشه یعنی واحد اجرایی قابل‌تخصیص** (Runtime)؛ برای سطح Taxonomy از «Taxonomy Task» استفاده می‌کنیم اگر لازم به تمایز باشد.

### Case در برابر Ticket
هر دو Instance‌ای هستند که یک مسئله را ردیابی می‌کنند، اما **Ticket** معمولاً یک چرخه‌ی عمر **خطی و ساده** دارد (باز → در حال کار → بسته) و اغلب یک Actor مسئول اصلی دارد — دقیقاً مدل `tickets` فعلی پروژه. **Case** معمولاً **غیرخطی** است: می‌تواند چند زیرفرایند موازی داشته باشد، چند بار باز/بسته شود، و چند Actor با نقش‌های متفاوت هم‌زمان روی آن کار کنند (مثلاً یک پرونده‌ی بازرسی ایمنی که تحقیقات، اقدام اصلاحی، و پیگیری حقوقی موازی دارد). **پیامد طراحی:** Ticket فعلی پروژه به‌عنوان یک **نوع خاص و ساده از Case** قابل مدل‌سازی است؛ Case Management عمومی‌تر می‌تواند در گام ۳ (موتور گردش‌کار) روی همان زیرساخت Work Item ساخته شود، بدون آنکه Ticket فعلی را بازنویسی کند.

### Form در برابر Request
**Form** یک قالب ساختاریافته برای جمع‌آوری داده است (تعریف فیلدها، اعتبارسنجی، نوع) — چیزی شبیه `form_templates`/`form_fields` فعلی پروژه. **Request** عمل/رویداد ارسال یک Form توسط یک Actor برای شروع یک Process است. یک Form می‌تواند بارها توسط Requestهای مختلف پر شود؛ یک Request همیشه دقیقاً به یک نسخه‌ی مشخص از یک Form وابسته است (نگاه کنید به [۱۵-versioning](15-versioning.md) برای اینکه اگر Form عوض شود، Instanceهای قبلی چه می‌شوند).

### Approval در برابر Decision
**Approval** یک نوع خاص و محدود از Decision است: یک Actor انسانی به یک گزینه‌ی از پیش تعریف‌شده (تأیید/رد، گاهی با توضیح) رأی می‌دهد و این رأی معمولاً یک Gate در مسیر اجراست. **Decision** مفهوم عمومی‌تر است: می‌تواند توسط یک انسان (Approval یک نمونه‌ی آن است)، یا توسط یک قانون خودکار (Business Rule/DMN Decision Table) گرفته شود، و لزوماً دو-گزینه‌ای هم نیست (می‌تواند بین N مسیر انتخاب کند). **پیامد طراحی:** `approvals`/`approval_steps` باید به‌عنوان یک نوع خاص از Work Item مدل شوند که خروجی‌اش یک Decision انسانی است؛ Decisionهای خودکار (Business Rule) نیازی به Work Item/Actor ندارند و مستقیماً توسط Rule Engine حل می‌شوند (نگاه کنید به [۱۴-rule-engine](14-rule-engine.md)).

### Business Rule در برابر Workflow
**Workflow** توالی/شاخه‌بندی **کنترل جریان** را مشخص می‌کند («بعد از این، برو به آن»). **Business Rule** یک تصمیم مستقل و **بدون‌حالت (Stateless)** است که ورودی می‌گیرد و خروجی می‌دهد، بدون آنکه بداند در چه فرایندی صدا زده شده («اگر مبلغ > ۱۰۰ میلیون، تأییدکننده = مدیر». طبق الگوی اثبات‌شده‌ی DMN/BPMN (نگاه کنید به [۱۴](14-rule-engine.md))، این دو باید به‌عنوان دو Entity کاملاً مجزا مدل شوند: یک Business Rule Task در Workflow فقط یک **ارجاع (Reference)** به یک Decision Table می‌دهد، نه اینکه منطق را در خود گراف Workflow Hardcode کند. این تفکیک یعنی: تغییر آستانه‌ی مبلغ تأیید نیازی به ویرایش گراف Workflow ندارد، فقط Decision Table عوض می‌شود.

## ۵. سایر مفاهیم (فهرست فشرده)

| اصطلاح | تعریف کوتاه |
|---|---|
| **Actor** | هر موجودیتی (انسان یا سیستم) که می‌تواند یک Work Item را انجام دهد یا یک Event تولید کند. |
| **Role** | یک برچسب انتزاعی که Actorها را بر اساس مسئولیت گروه‌بندی می‌کند (نه یک شخص خاص) — پایه‌ی Assignment قانون‌محور (نگاه کنید به [۱۳](13-role-assignment-model.md)). |
| **Responsibility** | پیوند بین یک Role/Actor و یک Work Item مشخص؛ می‌تواند «مسئول اجرا»، «مسئول تأیید»، یا «فقط مطلع (Informed)» باشد (الگوی RACI). |
| **Input / Output** | داده‌ای که یک Node/Activity قبل از اجرا نیاز دارد (Input) یا بعد از اجرا تولید می‌کند (Output) — پایه‌ی Variable Mapping بین Process اصلی و Sub-process (نگاه کنید به [۰۸](08-process-engine-architecture.md) بخش Reusable Sub-process). |
| **Artifact** | هر خروجی ملموس یک Process (سند، رکورد، فایل) که ارزش مستقل از خود Instance دارد. |
| **Document** | یک نوع خاص از Artifact که محتوایش عمدتاً متنی/فایلی است و چرخه‌ی عمر بازبینی/تأیید/آرشیو دارد. |
| **Record** | ردیف داده‌ی ساختاریافته در یک جدول کسب‌وکاری (مثلاً یک `org_members` یا `ticket`) — Artifact لزوماً Record نیست (یک PDF امضاشده Record نیست) اما هر Record می‌تواند Artifact تولید کند. |
| **Entity** | اصطلاح عمومی برای هر «چیز» قابل‌مدل‌سازی در Data Model (Process، Form، Role، …) — در این اسناد فقط برای اشاره به سطح داده استفاده می‌شود، نه سطح Runtime. |
| **Dependency** | رابطه‌ای که می‌گوید یک Node/Process نمی‌تواند شروع/تمام شود مگر Node/Process دیگری تمام شده باشد. |
| **Exception** | انحراف از مسیر طبیعی Workflow که نیازمند رسیدگی خارج از منطق پیش‌فرض است (خطا، شکست SLA، داده‌ی نامعتبر). |
| **Escalation** | نوع خاصی از واکنش به Exception یا نقض SLA: انتقال Work Item به یک Actor/Role با اختیار بالاتر. غیر-قطع‌کننده است (کار اصلی متوقف نمی‌شود؛ نگاه کنید به الگوی BPMN Escalation Event در [۰۶](06-process-patterns.md)). |
| **Notification** | پیام یک‌طرفه به یک Actor درباره‌ی رویدادی در Instance؛ برخلاف Work Item، نیازی به اقدام Actor برای ادامه‌ی Instance ندارد. |
| **Automation** | هر Node/Activity که بدون دخالت انسانی توسط سیستم اجرا می‌شود (معادل BPMN Service/Script Task). |
| **Event** | وقوع یک چیز در زمان مشخص که می‌تواند یک Instance را شروع کند، متوقف کند، یا مسیرش را تغییر دهد (Message، Timer، Signal، Error — طبق واژگان BPMN، نگاه کنید به [۰۷](07-workflow-node-catalog.md)). |
| **Trigger** | مکانیزم/شرطی که یک Event را به یک اقدام (شروع Instance، اجرای Node) وصل می‌کند. |
| **SLA** | تعهد زمانی روی یک Work Item/Instance («باید ظرف X ساعت پاسخ داده شود») — نگاه کنید به [۱۲](12-sla-and-escalation.md). |
| **KPI** | معیار عددی برای سنجش عملکرد یک Process در طول زمان (نرخ تکمیل به‌موقع، میانگین زمان چرخه) — سطح تحلیلی/گزارشی، نه Runtime. |
